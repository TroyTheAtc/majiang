# 麻前占卜算法说明

对应 H5 稳定版 **v2.0.7**。
算法实现：`src/js/fate.js`（唯一真源，本文件只是它的说明书）
渲染层：`src/js/divine.js`（不自行算档位，只从 `fate.getDay()` 取结果）

---

## 一、一句话概括

占卜结果是一个**确定性纯函数**：

```
(命主指纹, 日期) → 档位
```

同一人同一天**必然**得到同一结果；不同人同一天结果不同。
算法里没有任何 `Math.random()` 参与结果，**也完全不读战绩数据**。

这三个事实带来三个直接后果：

1. **历史可回溯**——`backfill()` 会给已有战绩的过去日期补算当日麻运，所以功能上线当天就有完整对账样本，不用等 30 天。
2. **对账不是循环论证**——如果占卜读了战绩，那“占卜 vs 战绩”的吻合率就毫无说服力。这是刻意的取舍。
3. **长按蓄力只是仪式**——结果在你按下之前就已确定；蓄力 1 秒只负责仪式感与防误触，松手 / 滑走即作废，不消耗任何随机性。

## 二、计算流水线

```
总分 score = 基线 0.5
           + 命主生克 relScore     ← 只在你填了生日时才有（±0.25）
           + 黄历日辰 dayFactor    ← 客观天时，与你是谁无关
           + 个人微扰 jitter       ← 只负责把“同一天的两个人”错开（±0.20）

档位 level = score 落进 4 段区间的哪一段   →  0 宜守 / 1 平 / 2 吉 / 3 大吉
```

```
        ┌─────────────┐
生日 ──▶│ 日柱天干→五行 │──┐
        └─────────────┘  │  生克关系
        ┌─────────────┐  ├──────────▶ relScore ─┐
日期 ──▶│ 阴历 / 干支  │──┘                     │
        └──────┬──────┘                         │
               │ 十二神·宿·宜忌·建除             ├──▶ + 0.5 基线 ──▶ 三阈值切档 ──▶ 结果
        ┌──────┴──────┐                         │
命主+日期 ─▶│ 确定性随机 │──▶ jitter ────────────┘
        └─────────────┘
```

三项相加再加基线 **0.5**，然后按 `0.1628 / 0.5698 / 0.9260` 三个阈值切四档。

## 三、因子① 命主生克（只在填了生日时生效）

取**出生日的日柱天干**定「日主五行」（`getDayMaster`），再和**占卜当天的日柱天干五行**比对。
因为打牌是求财，所以取「我克者为财」的逻辑：**我克的日子最好，克我的日子最差**。

| 关系 | 举例 | 文字 | 加减分 |
|---|---|---|---|
| 我克·得财 | 日主火，今日金 | 火克金 | **+0.25** |
| 生我·得助 | 日主水，今日金 | 金生水 | +0.08 |
| 比和 | 日主金，今日金 | 金与金比和 | 0 |
| 我生·泄气 | 日主土，今日金 | 土生金 | −0.15 |
| 克我·受制 | 日主木，今日金 | 金克木 | **−0.25** |

五行生克表：`木→火→土→金→水→木`（生）、`木克土、土克水、水克火、火克金、金克木`（克）。

> **没填生日**时这一项为 0，页面会引导填写，并说明「昵称不影响结果——改个名字不该改命」。

## 四、因子② 黄历日辰（客观天时）

和你是谁无关，按权重加减。数据来自历法库 `Solar` / `lunar-javascript`。

| 项目 | 取值来源 | 加减分 |
|---|---|---|
| 十二值日天神 | `getDayTianShenLuck` 为「吉 / 凶」 | ±0.22（黄道 / 黑道） |
| 二十八宿值日 | `getXiuLuck` 为「吉 / 凶」 | ±0.14 |
| 官方黄历宜忌 | `getDayYi` 含「纳财 / 开市」→ 加<br>`getDayJi` 含「纳财 / 开市」→ 减 | +0.18 / −0.18 |
| 建除值日 | `getZhiXing` 为 成 / 开 / 定 → 加<br>破 / 闭 → 减 | +0.10 / −0.14 |

> 宜、忌两项**可能同时命中**（例如“宜纳财”和“忌开市”），此时一加一减会相互抵消，属正常。
> 历法库没加载时，整项为 0（见第九节降级路径）。

## 五、因子③ 个人微扰

用 `mulberry32` 伪随机，**种子完全由「命主指纹 + 日期」决定**，取值域固定 **±0.20**：

```js
identity = 有生日 ? 'b:' + 生日 : 'd:' + 设备种子
jitter   = (rand01(identity, 日期, 1) - 0.5) * 0.40      // ∈ [-0.20, +0.20]
```

`rand01(identity, tag, slot)` 的实现要点：

1. `s1 = hash32(identity + '|' + tag, 0x9e3779b9)`、
   `s2 = hash32(tag + '|' + identity, 0x85ebca6b)`——正反各哈希一次，避免不同 tag 拼串后撞车；
   再异或 `slot × 2654435761` 混入序号。
2. 用 `mulberry32` 生成，**故意丢弃第一个输出**。种子直接参与首轮状态混合，首值与种子相关性偏强；
   实测（365 天分 8 桶）首值卡方 **22.0 → 丢首值后 3.0**，分布明显更均匀。
3. `tag` 是用途隔离：**取日运时 tag = 日期**，**取文案时 tag = `'hint'`**。

**命主指纹的作用**：`identityKey` 只用生日（或设备种子），**昵称不参与**——所以改昵称不会改命。
没填生日时用设备随机种子代替，**首次生成一次后持久化**（会话内还有一层 `memSeed` 记忆，防落盘失败导致同一天反复变结果）。

## 六、分档阈值与实测分布

```js
score < 0.1628            → 0 宜守
score < 0.5698            → 1 平
score < 0.9260            → 2 吉
score ≥ 0.9260            → 3 大吉
```

**校准口径**：跨 2026–2028 三年 × 100 个生辰交叉验证。

| 档位 | 目标占比 | 实测占比 | 单人区间（100 个生辰） |
|---|---|---|---|
| 宜守 | 20% | **19.6%** | 16~23% |
| 平 | 38% | **38.1%** | 33~44% |
| 吉 | 30% | **30.6%** | 25~35% |
| 大吉 | 12% | **11.7%** | 9~15% |

**温和性**：两个随机生辰在同一天的档位差分布——

| 档差 | 占比 |
|---|---|
| 0 档（完全相同） | 53.9% |
| 1 档（相邻） | 41.0% |
| 2 档 | 5.2% |
| 3 档（首尾对撞） | 0.0% |

即 **94.9% 落在相邻档以内**，不会出现“同一天一个宜守一个大吉”的割裂感。

## 七、结果如何落地

- **档位 → 插图**：`assets/images/` 下四张 WebP —— `yishou` / `ping` / `ji` / `daji`。
- **档位 → 文案**：每档备了 **8 组「谶语 + 行动建议」**，
  用 `rand01(seed, 'hint', 7)` 取下标选出。因为种子含命主指纹 → **同人同天同一句、不同人不同句**。
- **档位 → 缓存**：只把**档位**存进 `mahjong_divine_cache`（单条约 40 字节，保留 400 天），
  条目形如 `{ v: 2, ph: <profileHash>, lv: <档位> }`。缓存用 `profileHash` 绑定命主：
  **改生日 = 换命，缓存自动失效重算**；同时保证「当天不变脸」——当天补记战绩也不会让结果跳变。
  读缓存命中时仍会重新完整推演一遍（算法版本未变时二者必然一致），但**以缓存档位为准**。
- **依据透明**：页面把命主生克和每一条黄历加减分**列出来**（标「命」/「天」），
  不是只给一个结论，方便自己判断这个占卜“讲了什么理由”。

## 八、应验对账（占卜 vs 实际战绩）

| 当日档位 | 判定「应验」的条件 |
|---|---|
| 吉 / 大吉 | 当天**有赢**（当日金额合计 > 0） |
| 宜守 | 当天**未赢**（≤ 0），即「避损成功」 |
| 平 | 无倾向，**不参与**判定 |

只有**「当前命主算过」**的日期参与统计（`profileHash` 对得上），
所以改生日后旧样本会自动被排除，不会新旧混算。

页面展示**近 30 天**的命中率，并拆成「宜战 `a/b` · 宜守避损 `c/d`」两行——
因为“看涨看对”和“看跌看对”是两种能力，混成一个数会互相掩盖。

> `backfill()` 只补算**「有战绩记录」且 ≤ 今天**的日期，不预支未来。

## 九、降级路径

| 缺什么 | 表现 |
|---|---|
| **历法库没加载**（`Solar` 缺失） | `hasAlmanac = false`：黄历日辰项为 0，只剩基线 + 个人微扰。**结果依然确定、不报错**，`compute()` 全程 `try/catch`。 |
| **没填生日** | `hasBirth = false`：生克项为 0，只按天时推算。用设备种子代替指纹，页面引导填生日。 |
| **localStorage 写不进** | 复用 `data.notifySaveFailure()` 的「每会话只提示一次」，不重复弹提示。 |

## 十一、改参数 / 移植时的注意事项

1. **改比例必改阈值**。四档占比完全由 `TH_LEVEL` 决定，只改权重不改阈值会整体漂移。
   改完必须重跑 `majiang-fate-test.js` 的 [5] 全年分布断言（目标 20 / 38 / 30 / 12），
   以及 [4] 的温和性断言（相邻档 > 90%）。
2. **改算法必须同时升 `CACHE_V`**。否则老缓存里的旧档位会继续“命中”，
   用户看到的结果和重新推演的对不上。升 `CACHE_V` 后旧缓存自动作废重算。
3. **别把 `Math.random()` 引进结果计算**。只有 `deviceSeed()` 首次生成种子时允许用一次随机数
   （之后持久化固定），其余全部走 `hash32` / `mulberry32`。
4. **别让占卜读战绩**。`compute()` 的入参只有 `(dateStr, profile)`，看第二条约束即可确认；
   对账用的 `getVerification(records)` 是**独立的另一条链路**。
5. **移植到鸿蒙**：对应 `model/Fate.ets` + `pages/DivinePage.ets`。
   本算法无任何 DOM / 浏览器依赖（只用 `localStorage` 存档案与缓存），移植时把存储层换掉即可；
   历法库需要等价能力（日柱干支、十二神吉凶、宿吉凶、宜忌、建除值日）。
6. 测试文件在工作区根目录（不在仓库内）：`majiang-fate-test.js`（59 条断言，含确定性与分布校准）。
