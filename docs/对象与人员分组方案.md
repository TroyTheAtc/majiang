# 方案：对象（大类）+ 人员（具体人名）—— 定稿

> 状态：**暂不实施**（2026-10-08 三个决策已定，随后决定本次不做，**代码未做任何改动**；文档保留备查）
> 版本规划：将来若要做，版本号为 **v2.2.0**（加字段 = minor，与 v2.1.0 加底注同规则）

## 0. 已定决策（2026-10-08）

| 问题 | 决定 |
|---|---|
| 一场牌记几个人名 | **可以多选，一桌人都记** |
| 删掉/改名的人名，历史战绩还留不留在统计里 | **保留，永不丢**（并集口径，对象也一起改） |
| 人名怎么维护 | **一个输入框，逗号分隔**（人名行末尾 `+`，长按标签可删） |

一句话方案：给每条战绩多挂一个**可选的人名数组**，对象（大类）与对象表都不动。
录入时只有配了人名的对象才多出一行人名标签；没配的界面和今天一模一样。
统计新增「按人员」页签，「按对象统计」完全不动。历史数据没有人名 → 进「未指定」，
不提示补全、不报错、不影响任何旧口径。

## 1. 多选带来的三个连带后果（必须先说清）

选「一桌人都记」后，下面三条是必然的，不是可选优化：

### 1.1 存储是数组，不是单值

```js
persons: ['张三', '李四']     // 不是 person: '张三'
```

### 1.2 统计会重复计入 —— 各人合计之和 > 总额

同一场牌勾了张三和李四，那这一场的金额在「张三」和「李四」两个分组里**都算一整份**。

| 场次 | 对象 | 人名 | 金额 |
|---|---|---|---|
| 1 | 同事 | 张三、李四 | +300 |
| 2 | 同事 | 张三 | +100 |

→ 按人员统计：张三 **+400（2 场）**、李四 **+300（1 场）**，两者相加 +700，而这批牌总共只有 +400。

**这是正确行为，但必须付出代价：页面要写明**，否则你会以为统计算错了。
「按人员」页签上固定加一行小字：

> 同场多人会分别计入各自名下，各人合计之和大于总额。

明确**不做**金额分摊（每人分 1/3）：输赢本身就不是平摊的（一个人点炮，钱不是三个人一起出），
摊出来的数字看着精确、其实更假。

### 1.3 人名候选只来自当前对象

勾选的人名只从**当前选中对象**名下取，所以一场牌的人名天然同属一个对象（记录里仍保留 `category`）。
不会出现「同事·张三 和 家人·老婆 同场」。真遇到这种牌局，记主要的那一桌关系即可。
好处：`category` 依然是可靠的大类归属，按对象统计不受任何人名影响。

其余两个默认做法（要改直接说）：
- **上限 4 个**/场（一桌最多 4 人），超出拒绝添加
- **统计按人名合并**：「同事·张三」和「朋友·张三」如果都配了，统计里合成一个人（人只有一个）

## 2. 现状：能抄的资产，和必须正面处理的老问题

| 事实 | 位置 | 对方案的影响 |
|---|---|---|
| 对象是**纯字符串数组**，存在 `mahjong_categories` | `data.js getCategories` | 人员照抄这个模式就够，不需要树、不需要父子 id |
| 记录里存的是对象**名字快照**（不是引用） | `record.category` | 改名不影响历史 → 必须定「改名怎么办」 |
| 删除对象**不清理历史记录** | `data.js removeCategory` | 历史里会留「孤儿对象」，人员字段必须正面处理 |
| 按对象统计由**配置表驱动**（`CATEGORIES.forEach`） | `stats.js:243` | 删掉的对象在统计里**彻底消失**，分组之和 ≠ 总额 |
| 导入校验收紧到「对象必须在当前配置里」 | `transfer.js:26` | **已实测复现的 bug**，见 §2.1 |

### 2.1 顺手挖出来的一个真 bug（本次一并修）

`transfer.js` 的 `validateRecords()` 里有一行：

```js
if (cats.indexOf(r.category) === -1) return false;   // 记录的对象必须在当前对象列表里
```

而 `removeCategory()` 又不动历史记录，于是：

> **只要删过任何一个对象，之后导出的备份就再也导不回来了。**
> 提示只有一句「数据格式不符合要求」，看不出原因。

实测（jsdom 起真实页面 + 走真实粘贴导入路径，未改任何代码）：

```
当前对象列表：机场 / 家人 / 同事 / 同学 / 朋友
删掉「同学」→ true
库里 2 条记录，其中 category=同学 的 1 条
清空 → 粘贴导入这份备份 → alert：["数据格式不符合要求"] → 库里仍是 0 条
❌ 备份被拒 → 这份备份再也导不回来了
```

在「删除永不丢」的口径下这条必须修：统计里要保留删掉的对象/人名，备份却拒收它们，自相矛盾。
修法：校验放宽为「类型正确即可」，对象/人名是否还在配置表里**不作为导入的否决条件**——
配置表只该管"录入时候选什么"，不该管"历史数据是否合法"。

## 3. 数据模型

```js
// 记录
{ id, date, category: '同事', persons: ['张三', '李四'], location, amount, stake, dahu }
//                             ^^^^^^^ 新增；[] = 未指定（含全部历史数据）

// 配置：新增一个 key；对象表原样不动
mahjong_persons = { '同事': ['张三', '李四'], '家人': ['老婆'] }
```

为什么是「新字段 + 映射表」，不是树、不是 id 引用：

- **零迁移**：老记录没有 `persons` → 归一成 `[]`。这条路和当初加 `stake` / `dahu` 完全一样，已验证过。
- **不动对象表结构**：`mahjong_categories` 仍是字符串数组，老备份、老代码路径都不受影响。
- 用 id 引用人名（更抗改名）需要给全部历史记录做一次迁移，和"历史数据无法补全"的前提冲突。

归一化 `normalizePersons(v)`：不是数组 → `[]`；逐项 trim、去空、去重、单项限长 8 字、整表取前 4 个。

## 4. 录入交互：「不能太复杂」就落在这里

渐进式增强 —— 人名行只在「当前选中的对象配了人名」时才出现：

```
状态 A：选中「同事」，且「同事」下配了人名
  对象   [机场] [家人] [同事 ✓] [同学] [朋友] [+]
  人     [张三] [李四] [+]
               ↑ 多选，默认一个都不勾 = 未指定

状态 B：选中「机场」，没配人名（= 今天所有对象的现状）
  对象   [机场 ✓] [家人] [同事] [同学] [朋友] [+]
  （没有人名行，界面与今天完全一致）
```

- 人名一个都不勾 = 未指定，**永远不会挡住提交**，也不会让任何一次录入变多一步。
- 维护：人名行末尾 `+`，一次 prompt 输入（`张三, 李四` 逗号分隔，可整行替换）；长按标签出删除。
  全部复用现有 chip / longPress 代码，**不新增管理页面**。
- 编辑老记录：人名行全部未勾，不强求补全。
- 切对象联动：切到没配人名的对象 → 隐藏人名行并清空已勾人名（不把「张三」悄悄带到「家人」下面）。

## 5. 统计

| 页签 | 现状 | 本方案 |
|---|---|---|
| 按对象统计 | 大类分组 | 口径改成并集（§6.3），分组不变 |
| 按地点 / 按年份 / 按底注 | 已有 | 不动 |
| **按人员统计** | — | **新增**：按人名分组，`未指定` 置底、显示场次、页签下有小字说明（§1.2） |

- 详情卡直接复用：`getRecordsForStat` 加 `persons` 分支（`r.persons.indexOf(key) !== -1`），
  点「张三」看张三的局数 / 胜率 / 场均。
- 列表 meta 行：`茶楼·同事·张三/李四·底5`（单人就是 `同事·张三`）；人名不是金额，**不随「眼睛」隐藏**（与今日大胡一致）。
- 与占卜无关：占卜不使用战绩数据（v2.1.0 起），人员字段不影响占卜结果。

## 6. 三条必须定死的规则

1. **「未指定」是正式分组，不是待办事项**。历史数据永远进这里，页面不做「请补全人名」的引导，
   也不做批量补录界面。补不齐是前提，不是缺陷。
2. **改名 = 一次性批量改写历史**。把「张三」改成「老张」时，同步遍历记录把 `persons` 里的
   `'张三'` 改成 `'老张'`，并改配置表。几百上千条一次 JSON 读写，毫无压力。
   这个能力顺带能把现有「对象改名」的隐患一起解决。
3. **统计分组 = 配置表 ∪ 记录里出现过的值**（并集）。删掉的对象/人名仍以「已删除」标记出现在统计里，
   历史永不丢。副作用是好的：**顺带修掉现在「各分组之和 ≠ 总额」的老问题**。

## 8. 测试（沿用现有五套，dom 新增 [15] 一节，预计 +18 条）

- 表单：没配人名时**不出现**人名行（守住"不复杂"这条契约）；配了才出现；默认全不勾
- 多选：勾两个 → 存成两个；超过 4 个被拒；切对象清空越界人名
- 数据：老记录归一 `[]`；`normalizePersons` 去重 / 去空 / 限长 / 限个数
- 统计：一条记录同时进两个人分组（各自整份金额）；`未指定` 置底；点人名进详情卡只算含该人的场次；
  并集口径下**含已删除对象/人名的分组仍出现**
- 备份：导出带 `persons`；旧备份导入不报错；**删过对象/人名后仍能导入**（§2.1 的回归守卫）
- 反向验证：各处守卫逐个塞回，确认对应断言会红

## 9. 明确不做（防止范围蔓延）

- 不做人名管理独立页面（一个 prompt 足够）
- 不做「给历史记录批量补人名」的引导或界面
- 不做金额分摊（§1.2），不做对象 × 人员的交叉统计
- 不做两级下钻（对象详情卡里再列人名小计）——「按人员」页签已经能看到每个人
